# KB WODS: authentication and local-first cloud setup

This PR does not create a project, execute production SQL, configure remote Auth, deploy or merge. Use the **existing project named KB WODS**. Its actual project URL and public key were not available in this workspace; the committed configuration is deliberately empty. Local workouts continue without configuration. Do not substitute values from another project.

## Manual configuration in the existing project

1. In KB WODS → Project Settings / API, copy its project URL and **publishable key** (or legacy `anon` JWT). Fill the two empty strings in `src/cloud/config.js`. These are public browser configuration, not server secrets. The client rejects a `service_role` JWT or `sb_secret_` key. Never put privileged keys in HTML, JavaScript, localStorage configuration, a PR or GitHub Pages. An optional `window.KB_SUPABASE_CONFIG` object set before the module starts can provide the same public fields; tests use it without changing the committed configuration.
2. Review `supabase/migrations/202610220001_kb_cloud.sql`. Inspect the existing database first: this migration creates two new named tables and does not drop or migrate older prototype tables. If those names already exist, stop and reconcile their definitions; do not drop data or bypass the migration error. After **separate explicit authorization**, the project owner can apply this file once through the project's SQL editor or normal migration process. No application code runs DDL. Keep the normal project database backup before authorized schema changes.
3. Auth → Providers → Email: enable email/password sign-in and **Confirm email**. Configure production SMTP and review email templates/rate limits for your project. Registration displays a verification message and login requires a server-confirmed email. The default Supabase verification and password-recovery links redirect back with the Auth implicit-flow fragment. Custom templates must retain Supabase's confirmation URL and the requested redirect, rather than constructing app URLs containing passwords.
4. Auth → URL Configuration:
   - Site URL: `https://jozeless.github.io/kb-wod/`
   - Allowed redirect URL: `https://jozeless.github.io/kb-wod/`
   - For `npm start`: explicitly allow `http://127.0.0.1:8000/` and/or `http://localhost:8000/` if used.
   - For the automated subpath server: `http://127.0.0.1:8102/kb-wod/` (test emails need not be sent by automated tests).
   - Allow any additional local origin/path you actually use explicitly; avoid broad production wildcards. The client derives the redirect from the current origin and pathname, retaining the Pages subpath. Hash navigation does not need a server fallback.
5. Check the exposed `public` schema in the Data API and verify the RLS policies and grants before enabling cloud configuration for users. Supabase handles CORS and validates access JWTs. No service key is needed in the app. The migration explicitly grants schema usage/table CRUD to `authenticated`, revokes all table privileges from `PUBLIC` and `anon`, and checks ownership on both old and new rows for UPDATE.
6. After review and any future separately authorized release, close old PWA tabs so the waiting `kb2-static-v10` worker can activate. If public configuration is changed after a version was already installed, increment the static cache version again (and its test expectation) so installed clients receive the updated configuration. This PR itself does not publish anything.

## Data contract and isolation

- `kb_training_sessions`: composite primary key `(user_id, id)`; `user_id` references `auth.users`; stable original client UUID, workout ID/version, JSONB definition snapshot/results, original start/end timestamps and server-maintained `updated_at`. `session_data` contains the complete completed local envelope (including active duration, completion state and notes) for lossless history/recovery contracts. Only completed sessions are uploaded. Unfinished drafts remain in IndexedDB.
- `kb_weekly_plan`: composite primary key `(user_id, weekday)` and FK to `auth.users`. Seven recurring weekday slots are independent of session completion dates. A removal is an upserted row with **both** workout fields null; replacements preserve the selected version. The static workout catalog is not a database table, so a catalog FK would invalidate historical/unknown versions and is intentionally absent.
- Each table has owner-only SELECT/INSERT/UPDATE/DELETE RLS policies. Client user filters are convenience, never the authorization boundary. No production SQL is executed by tests.
- IndexedDB remains `kb2.training.sessions`, schema 1, store `sessions`; no database replacement or destructive migration. `ownerId` is additive metadata. Existing unowned records, IDs, results and timestamps remain intact. Completed records remain protected from draft overwrites and duplicate final saves.
- A draft created while signed in binds to that account on its first local commit; later account changes cannot reassign it. A draft created before login remains unclaimed, even if completed after login, and is offered for explicit import. Owned drafts/history are hidden from other accounts and from logged-out views. This is application-level separation, **not encryption against someone with browser/devtools/filesystem access**.
- The active recurring plan retains its existing `kb2.weekly-plan.v1` format. `kb2.cloud.guest-plan.v1` preserves the unclaimed plan; `kb2.cloud.account.v1:<user UUID>` stores each account's plan snapshot, last confirmed cloud base and acknowledgments. `kb2.cloud.workspace.v1` marks the current plan owner. Switching/logout preserves each plan and restores the appropriate workspace. Web Locks serialize workspace changes across supporting tabs. Stale-account responses cannot commit to the next user's workspace, and uploads read the account's snapshot rather than another account's active plan.
- First login never auto-imports unowned training history. Account shows the email and count and requires an explicit import confirmation. Claiming those sessions is transactional; repeated imports/upserts retain the UUID and do not duplicate records. Once claimed, those local records are not offered to another account. No local history is deleted after upload. Separate-browser copies of previously unclaimed data cannot reveal an ownership decision made elsewhere; import only data you recognize as yours.

## Synchronization behavior

Local completion commits first. Its owner-bound completed record is the durable outbox: all owned completed UUIDs without a confirmed acknowledgment are pending. There is no fragile in-memory-only queue. After a successful owned/id-matching upsert response, an acknowledgment is stored under that account. Lost acknowledgments safely repeat the same composite-key upsert; they never create another session.

The UI distinguishes **Saved locally**, **Sync pending** and **Synced**. Online status alone is never an acknowledgment. Import offers do not imply guest records have been uploaded. Failures keep the local record and expose an error in Account; retries run on login, online reconnection, completion, explicit Retry synchronization and every 15 seconds after a failed online attempt. Requests have a 15-second timeout where the browser supports `AbortSignal.timeout`. Account/revision checks fence late responses, and logout removes the local Auth session even if remote revocation cannot be confirmed.

Pulling history paginates in 500-row pages and stores the authenticated user's completed snapshots locally. It never replaces an existing draft or historical result. A UUID collision with another locally owned account aborts readback with an error instead of overwriting data. Synced means a past upload/download was confirmed, not that local data is a substitute for a database backup. The app provides no session-deletion or historical-edit UI in this phase.

The weekly plan is read before initial synchronization. Different local/cloud assignments show **Keep local plan** and **Use cloud plan**, with both sets of assignments visible. No upload or replacement occurs until that choice. Offline edits queue a dirty account plan; if the last known cloud base has changed, a conflict is shown again. Choosing cloud or local is explicit, including replacement/removal. The seven-row upsert is atomic, but the REST read/compare/write sequence is not a distributed compare-and-swap: simultaneous plan edits on multiple devices can still race after the comparison. Resolve via Account and retry; strong multi-device edit locking is outside this phase. Local snapshots are retained through the account workspace mechanism.

Passwords are never persisted by application code. Auth tokens persist at `kb2.cloud.auth.v1` to support login restoration; they are sensitive browser data. The app uses local ES modules and text DOM insertion, no third-party runtime script/CDN. Email callback tokens are removed from the address/history entry before network verification and requests suppress referrers. A previously verified cached identity can open its local data offline; this is not cloud authorization. Expired tokens must refresh before cloud access. A confirmed unauthorized response clears the in-memory identity; connectivity failures, server outages and rate limits keep cached local access. Email verification, password reset and server session revocation still depend on Supabase being reachable.

IndexedDB/localStorage may be evicted or unavailable and are not backups. No automatic deletion or cross-account reassignment occurs. Existing browser/OS interruption limits for active checkpoints remain. Device-scoped weight preferences and legacy prototype keys are not imported or rewritten. Cloud configuration, table unavailability or an Auth outage does not prevent guest local training. If account-owned local storage fails, the error is surfaced rather than claiming sync success.

## Verification

- `npm test`: injected Auth/API/synchronization tests plus all workout/timer/result regression tests. No real credentials or project needed.
- `npm run test:e2e`: Chromium mobile/desktop. Cloud tests use an in-memory HTTP mock and public test configuration; cover registration/recovery redirects, verification callbacks, persistent login/logout, account switching across tabs, explicit import, idempotency, failures, offline completion/recovery, cloud readback, weekly choices/removal, responsive layouts and all existing WOD/audio/PWA regressions. They do not send actual email or access KB WODS.
- `npm run test:rls`: requires Docker. Launches disposable PostgreSQL 17 with **no network/host port**, applies test-only Auth scaffolding, the exact migration and `supabase/tests/rls.sql`, then destroys the container. Tests exercise two real database roles/subjects: own CRUD, forbidden other-user reads/writes/deletes/inserts/owner reassignment, revoked anonymous grants and idempotent session upserts. `bootstrap.sql` is strictly for the disposable database; never run it in Supabase or another existing database.
- Before a future production release, manually verify actual email delivery/confirmation, expired/reset links, real project Auth redirects, grants/RLS with two test accounts, offline → online transitions on real iOS/Android, installed-PWA upgrades and remote logout behavior. This workspace has no KB WODS credentials/project connector, so live-project checks remain pending.
